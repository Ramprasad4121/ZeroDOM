## Scope Decision

The selected path is Approach B: Flight Recorder implementation.

ZeroDOM should keep the existing x402-compatible core and make the browser-agent
payment trace the center of the stage demo. The goal is not to add a broader
product surface before judging. The goal is to make the invisible transaction
visible: `402 -> sign -> replay -> 200`, with zero payment-specific DOM actions.

## Locked Requirements

### 1. First-Class Flight Recorder Event Layer

Status: REQUIRED

The current implementation proves the x402 payment loop, but the stage artifact
must make the transaction impossible to miss. Add a tiny recorder contract where
the Playwright/webcmd runner emits structured events and mirrors them into the
browser UI.

Required visible proof:

- Terminal/webcmd logs:
  - `[Intercept] HTTP 402 caught`
  - `[Signer] EIP-3009 authorization signed`
  - `[Execute] Replaying request with PAYMENT-SIGNATURE`
  - `[Unlock] 200 OK, premium resource unlocked`
- Browser-visible timeline: `GET -> 402 -> Sign -> Replay -> 200`
- Timer measured from caught unpaid `402` to paid `200 OK`
- Decoded `PAYMENT-REQUIRED`: amount, network, recipient prefix, nonce prefix,
  expiry
- Decoded `PAYMENT-RESPONSE`: payer prefix and mock-verification receipt
- Stage metric: `DOM payment actions: 0`

Out of scope for this requirement:

- Universal Playwright/CDP sidecar API
- Live on-chain settlement
- Real funds or personal wallet keys

### 2. Deterministic Payment Rejection Rescue

Status: REQUIRED

Every malformed, expired, replayed, wrong-network, wrong-amount, wrong-recipient,
or bad-signature payment must resolve to a controlled `402 Payment rejected`
response. A malformed `PAYMENT-SIGNATURE` must never produce a server crash or
generic `500`.

The server already catches invalid base64 JSON in `src/server.js`, but the
verification path in `src/payment.js` can still throw on malformed scalar fields
or invalid signature material. The plan must require a narrow verifier rescue
boundary that converts those failures into explicit rejection reasons.

Required behavior:

- Invalid base64 JSON: `402 Payment rejected`
- Missing accepted terms, authorization, or signature: `402 Payment rejected`
- Invalid `validAfter` or `validBefore`: `402 Payment rejected`
- Expired authorization: `402 Payment rejected`
- Unissued nonce: `402 Payment rejected`
- Spent nonce replay: `402 Payment rejected`
- Invalid signature bytes: `402 Payment rejected`
- Wrong amount, recipient, network, or asset: `402 Payment rejected`

Out of scope for this requirement:

- Production fraud engine
- External facilitator settlement
- Persisted database-backed nonce ledger

- Real on-chain settlement during the live demo.
- Any real merchant checkout or purchase execution.

## CEO Verdict

The current core is credible. The stage risk is perception and deterministic
failure handling, not protocol ambition. Lock the Flight Recorder and verifier
rescue requirements first; treat every other improvement as post-hackathon scope.

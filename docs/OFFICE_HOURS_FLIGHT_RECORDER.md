## Problem Statement

ZeroDOM needs to win a browser-agent hackathon by making one idea obvious in seconds:
payment should not be a browser checkout task. Standard browser agents get dragged
into fragile UI work: checkout pages, iframes, OTP, CAPTCHA, bot detection, and
slow cursor theatrics. ZeroDOM should show the alternative: the browser requests a
paid resource, the network layer handles HTTP 402, a disposable wallet signs, and
the resource unlocks before the DOM ever becomes a payment surface.

## What Makes This Cool

The cool moment is not the premium shopping report. The cool moment is that the
transaction has no checkout UI at all.

The memorable line is:

> Standard agents die at the checkout UI. ZeroDOM does not try to fill out forms;
> it moves the agent to the network layer, negotiates the HTTP 402 via an invisible
> EVM signature, and verifies the payment authorization deterministically in
> milliseconds. Production settlement can happen after the demo path.

The demo should be staged as a split-screen reveal:

1. Browser hits a paid endpoint and receives `402 Payment Required`.
2. Terminal logs show the invisible handshake: intercept, sign, replay, unlock.
3. Browser unlocks the premium dashboard in under 500 ms.
4. A visible counter reads `DOM payment actions: 0`.

The phrase to protect is: **Zero forms. Zero clicks.**

## Constraints

- Hackathon timing matters more than broad product architecture.
- The live demo must remain deterministic and stage-safe.
- No real funds, no personal wallet, no live merchant checkout.
- Stage copy should say "mock-verifies" or "locally verifies" instead of claiming
  live settlement.
- x402 v2 language must be used on stage:
  - `PAYMENT-REQUIRED`
  - `PAYMENT-SIGNATURE`
  - `PAYMENT-RESPONSE`
- `X-PAYMENT` may remain a compatibility alias in code, but it should not be the
  judge-facing story.
- Shopping intelligence is only the paid resource that makes the unlock legible.
  It is not the core product.
- The existing local server on port `4020` should stay stable; isolated tests can
  use `ZERODOME_PORT`.

## Premises

1. The remembered moment is sub-second DOM-less payment, not shopping data.
2. The opponent is checkout UI automation, not Stripe specifically.
3. Shopping intelligence is a prop that makes the paid resource legible.
4. Stage copy must use x402 v2 names, especially `PAYMENT-SIGNATURE`.
5. Mock settlement is acceptable for the demo because reliability beats testnet
   latency on stage.
6. The proof is strongest when judges can see both sides: browser on the right,
   terminal/webcmd payment trace on the left.

## Cross-Model Perspective

The independent cold read reinforced the same wedge: build ZeroDOM as a
browser-agent payment sidecar and expose a live payment flight recorder. The
strongest phrase it pulled out was:

> Zero forms. Zero clicks.

It recommended showing the network timeline as `402 -> sign -> replay -> 200`

remaining hackathon time improving the shopping dashboard.

The part to use now: Flight Recorder UI, timing, decoded headers, and failure

The part to defer: a full universal sidecar API like
`createZeroDomContext({ wallet, maxSpend, allowlist })`.

## Approaches Considered

### Approach A: Polished Split-Screen Script

Summary: Keep the current implementation and spend all remaining time on the
stage script, terminal logs, and rehearsal.

Effort: S

Risk: Low

Pros:

- Fastest path to a reliable live demo.
- Minimizes code churn before judging.
- Keeps the current verified x402 flow intact.

Cons:

- Judges may see it as a clever one-off demo rather than a reusable agent layer.
- The invisible payment could still be too invisible without a stronger trace.
- Less technical surface to discuss with webcmd founders.

Reuses:

- Existing Express paywall, Playwright demo runner, webcmd registration, and docs.

### Approach B: Flight Recorder Demo

Summary: Keep the current x402 core but make the payment trace the center of the
product. Add or emphasize a timer, `402 -> sign -> replay -> 200`, decoded header
fields, nonce/expiry checks, mock receipt, and `DOM payment actions: 0`.

Effort: M

Risk: Medium

Pros:

- Makes the invisible network payment visible to judges.
- Directly supports the chosen story: no checkout UI, no forms, no clicks.
- Gives webcmd founders the browser-agent magic they are likely to care about.

Cons:

- Adds some surface area close to the event.
- Needs careful visual restraint so the demo stays clear.
- Live failure toggles are out of MVP scope; replay/expiry proof stays in tests.

Reuses:

- Existing payment verifier, nonce/expiry/replay tests, terminal logs, browser UI,
  screenshots, and `ZERODOME_PORT` isolated verification.

### Approach C: Universal Sidecar Prototype

Summary: Turn ZeroDOM into a reusable Playwright/CDP wrapper that any browser
agent can attach to for x402 payments.

Effort: L

Risk: High

Pros:

- Best long-term developer-platform direction.
- Easier to explain as a reusable primitive after the hackathon.
- Natural path toward spend policies, allowlists, and protocol adapters.

Cons:

- Too much scope before judging.
- Could steal attention from the live demonstration.
- Requires API design and package ergonomics that are not needed to win tomorrow.

Reuses:

- Existing signer, server verifier, and Playwright interception pattern.

## Recommended Approach

Choose Approach B: Flight Recorder Demo.

This is the best hackathon move because it translates an invisible protocol
handshake into a visible stage artifact. The current implementation already proves
the core transaction. The missing piece is perception: judges need to see that the
agent never touched checkout UI.

The product surface should therefore become a payment flight recorder:

- Big network timeline: `GET -> 402 -> sign -> replay -> 200`.
- Millisecond timer from `402` interception to paid `200`.
- `DOM payment actions: 0`.
- Decoded `PAYMENT-REQUIRED` summary: amount, network, recipient, nonce, expiry.
- Decoded `PAYMENT-RESPONSE` summary: payer and mock-verification receipt.
- Clear safety line: disposable local key, mock settlement, no real funds.

### MVP Contract

The Flight Recorder is both terminal-first and browser-mirrored:

- Terminal/webcmd output is the source of truth for stage narration.
- Browser UI mirrors the same events so the audience can see the paid resource
  unlock without reading tiny terminal text.
- The implementation path is to emit structured events from the Playwright demo
  controller and forward the visible subset into `window.ZeroDOMDemo`.

Required event schema:

| Event | Required fields | Rendered state |
| --- | --- | --- |
| `request` | `method`, `url`, `startedAtMs` | GET node active |
| `payment_required` | `status`, `amount`, `network`, `payTo`, `noncePrefix`, `validBefore` | 402 node active, decoded invoice visible |
| `signed` | `scheme`, `walletPrefix`, `signaturePrefix`, `signedAtMs` | Sign node active |
| `replayed` | `headerName`, `url`, `replayedAtMs` | Replay log line visible |
| `unlocked` | `status`, `elapsedMs`, `receiptMode`, `payerPrefix` | 200 node active, premium report unlocked |
| `rejected` | `status`, `reason`, `elapsedMs` | Failure log visible in headless/test path |

The 500 ms timer is measured from the moment Playwright receives the unpaid
`402` response to the moment the replayed request receives paid `200 OK`. It
does not include the first browser navigation or the user's demo-start click.

`DOM payment actions: 0` means the agent performed zero clicks, text entry,
iframe interactions, form submits, or button searches for payment-specific UI
after the paid endpoint returned `402`. The button that starts the demo is not
a payment action. This should be displayed as a stage metric and backed by code
structure: the payment path signs and replays through headers, not DOM selectors.

### Scope Split

Must ship before judging:

- Terminal logs with the stage wording:
  - `[Intercept] HTTP 402 caught`
  - `[Signer] EIP-3009 authorization signed`
  - `[Execute] Replaying request with PAYMENT-SIGNATURE`
  - `[Unlock] 200 OK, premium resource unlocked`
- Browser-visible timeline: `GET -> 402 -> Sign -> Replay -> 200`.
- Timer for `402` receipt to paid `200`.
- `DOM payment actions: 0`.
- Decoded invoice summary: amount, network, recipient prefix, nonce prefix.
- Safety line: disposable local wallet, mock local verification, no real funds.

Nice for Q&A, not live-stage required:

- `npm run self-test` proof that replayed nonce returns `402`.
- `npm run self-test` proof that expired authorization returns `402`.
- A short explanation that recipient, network, and amount are also verified by
  the server before unlock.

Post-hackathon:

- Wrong-recipient UI toggle.
- Full universal Playwright/CDP sidecar API.
- npm package, examples, and CI release pipeline.

## Open Questions

- Canonical stage layout: terminal/webcmd trace on the left, browser on the
  right. The browser may mirror the Flight Recorder, but the split-screen layout
  is the default.
- Should the premium payload remain shopping intelligence for this event, or be
  swapped later for security intel, market data, or paid agent memory?

None of these block the recommended demo strategy.

## Success Criteria

- A judge understands in 30 seconds that ZeroDOM avoids checkout UI entirely.
- The visible flow shows `402 -> sign -> replay -> 200`.
- The measured replay path, from caught `402` to paid `200`, completes in under
  500 ms on the demo machine. If it exceeds 500 ms, still show the exact timing
  rather than hiding it.
- The UI or terminal shows `DOM payment actions: 0`.
- Stage language uses `PAYMENT-SIGNATURE`, not `X-PAYMENT`.
- Replay and expiry protections remain demonstrably enforced.
- The demo can fall back to `ZERODOME_PORT=4022 npm run demo:headless`.
- The stage server on `127.0.0.1:4020` remains stable.

## Stage Preflight And Fallbacks

Run these before presenting:

```bash
curl -s http://127.0.0.1:4020/api/health
zerodome --help
webcmd zerodome demo:headless
ZERODOME_PORT=4022 npm run self-test
```

Fallback matrix:

| Problem | Primary response | Fallback |
| --- | --- | --- |
| Port `4020` already occupied | Keep the live server if health is OK | Use `ZERODOME_PORT=4022 npm run demo:headless` |
| `webcmd` command not registered | Run the README registration command | Use `npm run demo` directly |
| Browser launch fails | Retry once with default Playwright profile | Run `npm run demo:headless` and narrate terminal output |
| Payment timeout | Show exact elapsed time and self-test proof | Restart on isolated port with `ZERODOME_PORT=4022` |
| Unlock exceeds 500 ms | Treat as slower but still deterministic | Emphasize no DOM actions and verified retry path |
| Projector makes terminal unreadable | Browser UI mirrors the recorder events | Zoom terminal font before starting |

## Distribution Plan

For the hackathon, distribution is local:

- User runs `webcmd zerodome demo`.
- The project remains a local Node package with a linked `zerodome` binary.
- The server binds to localhost and uses a disposable local wallet.

For a post-hackathon developer artifact:

- Package the browser-agent payment wrapper as an npm package.
- Provide a CLI command for registering the webcmd external command.
- Publish examples for Express and Playwright.
- Add CI that runs:
  - `npm run self-test`
  - `ZERODOME_PORT=4022 npm run demo:headless`
  - replay and expiry tests
